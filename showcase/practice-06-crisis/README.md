# Практика 6 Антикризисная стратегия проекта Допуск

Кейс 3 «Негатив в СМИ».

## Исходные условия

В модельном сценарии «Допуск» проходит пробное внедрение в компании. Один из пользователей публикует сообщение о том, что облачный ИИ-агент получил значения из закрытого поля таблицы. Публикацию подхватывают профильные СМИ, а потенциальные клиенты начинают сомневаться в защите данных. Заранее подготовленного порядка реагирования у проекта нет.

На момент обращения известен факт публичного обвинения, но ещё не установлено, действительно ли произошла запрещённая передача данных и связан ли её источник с «Допуском».

## Задание 1 Анализ кризисной ситуации

### Характер и возможные причины кризиса

Ситуация представляет собой репутационный кризис с возможной технической причиной. Для проверки нужно установить, получил ли агент закрытые значения, когда это могло произойти, какие правила действовали и каким способом данные могли попасть в ответ.

| Возможная причина                                | Что нужно проверить                                                                                                                                                                                                                |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ошибка в проверке результатов          | Не могли ли закрытые значения пройти через таблицу, подпись графика, сообщение об ошибке или ранее сохранённый результат в ноутбуке. |
| Ошибка в настройке доступа                | Соответствовали ли действовавшие правила ограничениям клиента, было ли нужное поле действительно закрыто.                                               |
| Непонятное подтверждение передачи | Видел ли пользователь конкретный результат перед отправкой и понимал ли, что разрешает передать его облачному агенту.                           |
| Передача через другой инструмент    | Не загружался ли тот же файл напрямую в облачный сервис или через другое подключение агента.                                                                           |

Отдельная причина развития кризиса — отсутствие согласованной реакции. Основатель одновременно занимается разработкой, проверкой обращения и общением с клиентами. Если технический разбор занимает всё время, публичное сообщение остаётся без ответа, а неопределённость усиливает недоверие.

### Возможные последствия

Для клиента подтверждённая передача закрытых данных означает раскрытие информации, которую он рассчитывал сохранить внутри компании. Может потребоваться остановка работы с агентом и проверка других результатов анализа.

Для «Допуска» кризис может привести к прекращению пробного внедрения, отказам потенциальных клиентов и дополнительным расходам на исправление и независимую проверку. Разработка новых функций замедлится. Даже если связь с продуктом не подтвердится, объяснение результатов проверки потребует времени.

### Первичные меры стабилизации

Сначала я связываюсь с автором обращения и ответственным за данные со стороны клиента. Совместно с ИТ-представителем клиента приостанавливаю передачу результатов агенту в затронутой установке до выяснения обстоятельств. Если границы проблемы неизвестны, ограничение должно охватывать всё подключение «Допуска» в этой установке.

Одновременно необходимо сохранить сведения для проверки: время обращения, версию продукта, действовавшие правила и доступную историю действий. При признаках продолжающейся передачи её остановка имеет приоритет. Материалы с конфиденциальными значениями остаются в среде клиента; для воспроизведения ошибки по возможности используется пример с искусственными данными.

Публично нужно подтвердить получение обращения и назвать время следующего сообщения. Отключение передачи ограничивает дальнейший риск, но не возвращает сведения, которые уже могли попасть в облако.

## Задание 2 Разработка антикризисной стратегии

### Выбранный подход

Предлагаю временно ограничить затронутое подключение, провести проверку совместно с клиентом и регулярно сообщать о ходе работы. До установления причины нельзя обещать, что данные в безопасности или что проблема будет исправлена к определённому часу.

Такое решение прервёт часть аналитических задач клиента. Однако продолжение работы при неизвестной причине может увеличить объём раскрытой информации. На время проверки клиент сможет использовать локальный ноутбук без подключения облачного агента через «Допуск».

### Распределение ответственности

| Участник                                                                | Ответственность                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Я как основатель и разработчик                        | Координирую действия, проверяю работу продукта, готовлю исправление, веду журнал событий и отвечаю на обращения пользователей и СМИ.              |
| ИТ-представитель клиента                                  | Ограничивает подключение в инфраструктуре компании, сохраняет доступные технические сведения и помогает проверить восстановление работы. |
| Ответственный за данные со стороны клиента | Уточняет, какие сведения должны были оставаться закрытыми, оценивает последствия для компании и согласует условия возобновления передачи.  |

### План действий

| Срок с момента получения обращения   | Действия                                                                                                                                                                                                                                                                  | Ожидаемый результат                                                                                                                                                                |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Первые 30 минут                                         | Зафиксировать обращение, связаться с клиентом, начать ограничение передачи и сохранение сведений. Отложить несрочную разработку.                                   | Определены участники проверки, приняты меры против дальнейшей передачи.                                                                |
| Первые 1–2 часа                                         | Уточнить содержание обвинения, проверить правила и доступные записи о действиях. Опубликовать первое сообщение.                                                                   | Есть перечень известных фактов, вопросов и время следующего обновления.                                                                 |
| В течение первых суток                          | Проверить основные гипотезы, попытаться воспроизвести ситуацию на искусственных данных, выяснить, может ли проблема возникнуть у других клиентов.    | Подготовлены промежуточные выводы и дальнейшие действия. При необходимости предупреждены другие клиенты. |
| После установления причины                 | Исправить ошибку или настройки, повторить проблемный сценарий, проверить другие способы выдачи результатов. Согласовать восстановление с клиентом. | Получены результаты проверок, достаточные для решения о возобновлении работы.                                                     |
| В течение месяца после стабилизации | Описать причины и принятые меры, обновить инструкцию реагирования.                                                                                                                                                       | Понятно, как распознать и обработать повторную ситуацию.                                                                                             |

### Коммуникационная стратегия

Все сообщения от проекта готовлю я. Технические сведения сверяю с материалами проверки, а раскрытие информации о клиенте согласую с его представителем. Для клиента используется согласованный закрытый канал, для публичных обновлений — одна страница на сайте проекта. Ответы СМИ должны ссылаться на неё, чтобы разные публикации не содержали противоречащих друг другу объяснений.

Пример первого сообщения, если обращение поступило утром:

> Нам известно о сообщении о возможной передаче закрытых данных при использовании «Допуска». Мы связались с пользователем и начали проверку. Сейчас выясняем, какие данные получил агент и каким способом они были переданы. Следующее обновление опубликуем сегодня до 18:00 на этой странице. Просим не размещать конфиденциальные сведения в открытых комментариях.

В каждом обновлении указываются установленные факты, выполненные действия и время следующего сообщения. Пока проверка продолжается, предлагаю публиковать обновления ежедневно, даже если новых выводов нет. О подтверждённой угрозе затронутых клиентов необходимо уведомлять сразу.

Публичные объяснения не должны содержать закрытые значения, полные журналы или материалы клиента. Критику следует обсуждать по существу. Требование удалить публикацию до окончания проверки может усилить конфликт.

### Действия по результатам проверки

| Результат                                                                                              | Дальнейшие действия                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Подтверждена ошибка «Допуска»                                                        | Сообщить затронутым клиентам, какие сведения могли быть переданы, устранить причину и проверить исправление. Опубликовать объяснение без раскрытия данных клиента. |
| Обнаружена ошибка настройки или непонятное подтверждение     | Исправить настройки, уточнить инструкцию или интерфейс и повторно согласовать правила. Проверить, не сталкиваются ли с той же трудностью другие пользователи.            |
| Установлено, что передача произошла через другой инструмент | Объяснить клиенту установленный путь передачи, подготовить публичное уточнение в допустимом объёме и предложить СМИ обновить материалы.                                                  |
| Сведений недостаточно                                                                       | Сохранить необходимые ограничения, перечислить открытые вопросы и продолжить проверку. Не объявлять обвинение опровергнутым.                                                                      |

Подключение возобновляется после проверки исходного сценария, включая ранее сохранённые результаты, и согласования с клиентом. Закрытые значения должны оставаться локально, разрешённые результаты — передаваться, а неоднозначные — ожидать решения человека.

### Оценка стратегии

Сильная сторона выбранного подхода — клиент понимает, кто занимается проблемой, какие действия уже выполнены и когда ждать следующего сообщения. Ограничение передачи уменьшает вероятность продолжения ущерба, а проверка нескольких гипотез помогает установить причину.

Главное ограничение связано с ресурсами: один основатель не сможет одновременно быстро расследовать сложную ошибку, отвечать всем пользователям и продолжать разработку. Поэтому новые функции временно откладываются, а при недостатке компетенций потребуется внешний специалист. Дополнительный риск — затянувшаяся остановка работы клиента, которую придётся отдельно учитывать при согласовании дальнейшего внедрения.

## Задание 3 Адаптация к изменениям рынка

### Сценарий изменения рынка

Предположим, что после подобных публикаций компании стали осторожнее подключать облачных ИИ-агентов к внутренним данным. При выборе продукта они запрашивают подтверждения того, как контролируется передача информации. Конкуренты также начинают делать акцент на защите данных и демонстрировать свои проверки.

В этих условиях описания функций «Допуска» недостаточно для решения о внедрении. Клиенту нужно увидеть, как ограничения работают на его задачах. Основное назначение продукта сохраняется, но порядок развития и подготовки внедрений меняется.

### Изменения в стратегии проекта

| Направление                     | Что предлагаю изменить                                                                                                                                                                                                                                                                     | Какой результат нужен                                                                                                                                                                                |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Приоритеты разработки  | Сначала устранить подтверждённые недостатки контроля выдачи и добавить проверки повторения ошибки. Расширение функций продолжить после этого.                                      | Обновления не возвращают уже выявленную проблему.                                                                                                                            |
| Пробное внедрение          | До подключения конфиденциальных данных проводить демонстрацию на искусственном наборе: разрешённая сводка, запрещённое поле и результат, требующий подтверждения. | Клиент понимает поведение продукта и согласует правила передачи.                                                                                                |
| Работа с пользователем | Понятно показывать, какой результат отправляется агенту. | Продвижение                     | Описывать проверенные возможности и ограничения, показывать примеры работы.                                                                                                                                                                 | Ожидания клиента соответствуют назначению продукта: разрешённые результаты передаются, закрытые остаются локально. |
| Проверка потребностей  | Обсуждать с представителями текущего пробного внедрения и потенциальными клиентами, какие сомнения мешают начать работу.                                                                              | Следующие изменения опираются на конкретные причины отказа и требования к проверке.                                                             |

Сначала устраняются причины инцидента, затем обновляются демонстрация и инструкция. Следующие изменения определяются по результатам обсуждения с клиентами.

### Проверка результата

Через месяц после стабилизации предлагаю проверяется выполнение плана по следующим признакам:

- Установлена причина обращения либо записаны оставшиеся вопросы и действующие ограничения.
- Исходный проблемный сценарий включён в проверки; их результаты сохранены.
- Затронутый клиент получил объяснение и решение по дальнейшей работе.
- Сообщения публиковались в объявленное время, инструкция реагирования обновлена.
- Для новых запросов на внедрение фиксируются причины отказа и результат обсуждения требований к защите данных.

Для оценки доверия я буду учитывать, согласился ли клиент продолжить пробное внедрение и какие вопросы остаются у потенциальных заказчиков.
